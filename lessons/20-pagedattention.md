# 20｜每個人的回答長度不同，KV 空間怎麼分？

若每個請求都預留最大 context 的連續空間，短請求會浪費大量記憶體。若隨長度不斷搬動整個 cache，又增加資料複製成本。問題出在動態增長的狀態如何配置。

PagedAttention 把邏輯上的連續 token 分成區塊，透過對照表找到實際記憶體位置。這些實體區塊不必相鄰；attention 核心按照映射讀取它們。

| 邏輯 token 範圍 | 實體區塊（示意） |
| --- | --- |
| 0–3 | block 7 |
| 4–7 | block 2 |
| 8–11 | block 9 |

假設 block 容量 4 tokens，請求長度 10，需配置 3 blocks，共 12 個位置；尾端浪費 2 個。若預留 32 個連續位置，則浪費 22 個。這是本課自訂算例，不是實際框架的固定 block 大小。

分頁主要改善配置、碎片與共享。若所有 token 的 KV 都仍需保留，其有效資料量並沒有因分頁而消失。區塊越小，尾端浪費越少，但 mapping 與管理成本可能提高。

和作業系統分頁的類比可以幫助理解，但這不表示資料必然換到 CPU RAM 或磁碟。區塊可以全部仍在 GPU 記憶體；是否 offload 是另一個設計問題。

多個請求若有相同且可安全共享的前綴，可能共用對應 blocks。當其中一個分支需要修改共享區塊時，必須處理 copy-on-write 或其他隔離機制，不能讓一個請求破壞另一個。

**練習：** block 容量 16，兩個獨立請求長度各為 17，沒有共享時共需幾個位置？

**答案：** 各需兩個 blocks，共 64 個位置，其中 34 個有用、30 個是尾端餘量。不能只對總 token 數 34 取整後配置三個 blocks，除非另外設計跨請求共享配置方式。
