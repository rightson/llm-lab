# 16｜「每秒幾個 token」其實不夠回答快不快

有人在意按下送出後多久開始看到字，有人在意長文多久完成，服務經營者則在意同時能服務多少人。這些是不同指標，不應用一個 tokens/s 取代。

| 指標 | 要回答的問題 |
| --- | --- |
| TTFT | 請求開始到第一個輸出 token，等多久？ |
| ITL | 相鄰輸出 token 的時間間隔是多少？ |
| TPOT | 每個後續輸出 token 平均花多少時間？ |
| End-to-end latency | 完成整個請求要多久？ |
| Output throughput | 系統每秒交付多少輸出 tokens？ |
| Goodput | 每秒完成多少符合指定品質與延遲目標的工作？ |

若從客戶端 t₀ 發送，第一個 token 在 t₁、最後一個在 tₘ，且 m>1，常見平均 TPOT 定義是 (tₘ−t₁)/(m−1)。只有一個輸出 token 時，此定義不適用。輸入吞吐與輸出吞吐要分開，不能把 prefill tokens 加進去冒充生成速度。

假設 TTFT=0.5 秒、產生 101 個 token、後續平均間隔 0.02 秒，則最後 token 約在 2.5 秒出現。單一串流後續速度約 50 tokens/s，但它不代表整個服務的總吞吐。

另一個陷阱是只報平均。大多數請求很快、少數等十秒，可能對互動服務非常糟。至少觀察 p50、p95，並在足夠樣本下看 p99；也要保留失敗、取消與 timeout，不能只統計成功的快請求。

**練習：** A 系統總吞吐更高，但 p95 TTFT 從 1 秒變 8 秒，能說 A 一定較好嗎？

**答案：** 要看服務目標。離線批次可能接受，互動助理可能不行。

**量測規格：** 記錄模型、硬體、精度、輸入/輸出長度分布、併發、到達率、是否 warmup、cache 命中率與計時位置。沒有這些背景，跑分通常無法公平比較。
