# 教學與實驗標準：用可驗證的直覺維持主線

## 三層的教學對應

課程主要組織為「LLM 模型理解 → 演算法程式設計 → NPU 部署加速」。每篇標示它的主要層面，以及它接收或產生什麼成果；不用每篇強塞全部三層。

第一層須交代設計原因及訓練/推理中的作用；第二層須將規格變成可核對的程式；第三層須將程式算子映射到硬體執行，驗證結果並比較成本。下方數學、程式、系統、硬體的深度分層是敘述方法，不取代這三層架構。

## 一課的起點與終點

起點是一個讀者能理解的困惑，例如「為什麼加長 prompt 後，每個新 token 也慢了？」；終點是讀者能解釋、預測並驗證一個機制。文章名稱盡量表達這個問題或結論，不能只是堆疊 API、縮寫或工具清單。

先在簡化條件下把概念講清楚，再於會影響判斷的位置交代限制。不要在正式推導之前堆滿不相干的邊界聲明，也不要用類比取代真正的運算與證據。

## 每課應包含的內容

1. **具體現象與核心問題。** 讓讀者知道為什麼值得理解。
2. **第一版直覺。** 用熟悉例子建立暫時模型，明講哪一部分只是類比。
3. **最小手算例。** 維度、數值、單位與輸出可逐步核對；公式符號首次出現便定義。
4. **一張有資訊量的圖或表。** 例如 token 對齊、張量 shape、gradient flow、cycle timeline；圖中的數字須與算例一致。
5. **對應程式。** 指出算例落在哪個函式與變數。新手不需要先讀整個框架。
6. **先預測再實驗。** 明列要改的因素、預期方向，以及會推翻解釋的結果。
7. **一個反例或失敗案例。** 訓練失敗、錯誤 mask、精度下降、buffer hazard 等，應與本課問題直接相關。
8. **理解檢查與下個問題。** 包含新的輸入或 shape；有解析，不只重複正文。

這是內容要求，不必把八個標籤機械地當作每篇標題。成熟的敘述可以自然串起來。

## 深度分層

| 層次 | 讀者得到什麼 | 何時引入 |
| --- | --- | --- |
| 核心敘述 | 為何存在、如何運作、如何判斷 | 每一課 |
| 數學推導 | 精確的計算與條件 | 解釋需要時，先補最小先備 |
| 程式實驗 | 操作輸入、比對與干預 | 每個核心機制都要有落點 |
| 系統延伸 | 記憶體、I/O、排程與成本 | 理解運算後 |
| 硬體延伸 | 數值契約、cycle、RTL、實體限制 | 與 LLM 問題對齊後 |

進階段可以很深，但應清楚標記進入所需先備，並提供回到主線的位置。不能要求讀者先懂 STA 才理解 attention 的功能。

## 實驗的四層 reference

| 比對層級 | Reference / DUT | 結論範圍 |
| --- | --- | --- |
| 數學 | 手算或簡單獨立實作 / 向量化程式 | 公式與 shape 是否正確 |
| 學習 | 固定資料 split、baseline / 受訓模型 | 在所測資料與預算下是否學到任務、是否泛化 |
| 數值 | 浮點 / 明確規格的整數近似 | 誤差、任務品質與容差取捨 |
| 硬體 | bit-accurate model / RTL simulator | 數值、協定與建模的時序是否符合規格 |

同一份錯誤函式被兩邊共同呼叫，不足以建立獨立驗證。RTL 檢查優先共用輸入向量與規格，避免 reference 重複 DUT 的控制邏輯。不同近似層級採不同比較方式：整數 kernel 可以要求 bit-exact；浮點與量化模型則需事前指定容差與任務門檻。

## 如何避免錯誤的「理解」

- Loss 下降只表示優化目標改善；必須另外看 held-out 資料。
- Hidden-state 圖看起來成群，不直接等於學到人類命名的概念。
- Attention 圖描述一次運算的權重；因果主張還需適當干預與對照。
- Ablation 的差異可能同時來自參數量、訓練預算或不穩定性；要記錄混雜因素。
- 一個小型合成任務的成功，不等於解釋所有 LLM 能力；失敗也未必能否定整類架構。
- 相同最終 token 不代表 logits 完全相同；不同最終 token 也不自動表示硬體錯誤，需先查看近似誤差與採樣。
- Cycle model、RTL simulation、STA、PPA 與實際矽結果要分開標記。

## 每個可重現實驗的最小紀錄

Problem、假設、輸入/shape、資料生成或來源、split、seed、模型設定、程式版本、依賴版本、命令、預期性質、觀察結果、結論與限制。訓練實驗另記 optimizer、步數、預算與 checkpoint；效能實驗另記 warmup、重複次數、計時邊界與硬體。

第一版訓練任務以 CPU 可執行的小配置為目標；實际完成時間要量測後再承諾。PyTorch/MPS/GPU 可作延伸，不讓大型下載或商用 API 成為基本理解的必要條件。

## 防止課程偏離的發布檢查

新增內容必須答得出以下問題：

1. 這篇改善哪個 LLM mental model？
2. 讀者能新增哪一項可驗證的預測能力？
3. 它在既有問題上增加深度，還是只增加新名詞？
4. 若是硬體課，它對應哪個模型算子、資料形狀或精度限制？
5. 新增的是已跑過的教材/實驗，還是尚待實作的設計？狀態是否一致？

若只是在加入工具操作或硬體功能，先放進對應技術附錄，直到能接回主線問題。程式修改仍依實際風險做驗證；純文件規劃不用為了增加測試數量重跑無關測試。
